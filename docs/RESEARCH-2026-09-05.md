# Research Snapshot — 2026-09-05

## Summary

The strongest project opportunity is not another generic browser WebMCP wrapper. JavaScript framework helpers, polyfills, bridges, inspectors, site/tool generators, and OpenAPI/MCP conversion paths are already emerging quickly.

The more defensible seam is **stateful server-driven application actions** where execution depends on active UI/session/component context and where an endpoint-first description is incomplete.

## Confirmed ecosystem signals

### WebMCP

- Developed through the W3C Web Machine Learning Community Group.
- Experimental/draft status; not a W3C Recommendation.
- Browser API has evolved materially, including the move toward `document.modelContext` and lifecycle/security refinements.
- Explicitly oriented toward collaborative human-in-the-loop web workflows rather than replacing backend integrations.

### Framework-specific integrations are appearing

Examples observed during research include:

- Laravel/Livewire WebMCP packages.
- WordPress Abilities → WebMCP bridges.
- React/Vue/Angular/Svelte helpers.
- Phoenix/Ash + LiveView integrations exposing resource actions and per-view UI state.
- Rails helpers/experiments.
- Browser/MCP bridges and generated tool systems.

This validates the problem but weakens any “nobody has done framework integration” claim.

## Gap statement

A more accurate gap is:

> Framework-specific solutions are emerging in isolation, while there is no broadly established protocol-neutral contract separating action semantics, runtime binding, trusted state, and agent-surface projection across stateful server-driven UI frameworks.

SurfaceRelay should compete on that architectural seam plus a strong Laravel/Filament reference implementation.

## Why OpenAPI is secondary

OpenAPI is excellent where an explicit HTTP API is already the application boundary. It does not naturally encode runtime facts such as:

- currently mounted component instance;
- current unsaved draft;
- current selected table records;
- active UI filters;
- current modal/wizard step;
- browser/session-scoped state.

An OpenAPI importer can later map endpoint actions into SurfaceRelay, but it is not the core differentiation.

## Why HTMX is the portability proof

HTMX can sit in front of many languages/frameworks. A shared Action/Binding contract working for Livewire and HTMX is stronger evidence of portability than writing a second PHP framework adapter.

## Positioning

Preferred technical description:

> A contract and adapter architecture for exposing stateful, server-driven web application actions to AI agents without duplicating application logic or creating parallel agent-only APIs.

Avoid:

- “replacement for MCP”;
- “official WebMCP framework”;
- “LSP for agents” as a literal protocol claim;
- “first framework integration” claims.
