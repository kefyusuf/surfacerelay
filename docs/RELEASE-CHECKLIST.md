# Release-candidate evidence checklist

This checklist reviews local experimental candidates. It is not a publication
workflow, release approval, or claim that integrated release verification is
complete. The two existing builders and consumer guides remain independent;
same-revision/two-artifact orchestration and aggregate evidence belong to T-805.

## Candidate inputs and source

- [ ] Record one exact full 40-character source SHA and verify the checkout matches
  it with no tracked or untracked changes before tooling runs. Use an archived
  snapshot of that revision; ignored dependencies or local source edits must not
  become candidate inputs.
- [ ] Select an explicit internal SemVer prerelease accepted by the existing
  tooling. `0.0.0-alpha1` is the current verification input, not a public version.
  Record the intended version for both candidates; do not infer synchronized
  public package streams from this shared input.
- [ ] Keep source manifests unchanged. Allocate empty real staging directories
  and isolated consumer directories; preserve prior evidence instead of silently
  overwriting it. Avoid source links, workspace dependencies and symlink installs.
- [ ] Record actual host/runtime versions and prerequisite availability, including
  Python dependencies, Git, Node/npm, PHP extensions and Composer as applicable.

## Existing artifact and consumer checks

- [ ] Follow the [Laravel consumer guide](consumers/laravel.md) with the recorded
  source/version input. Build and validate the ZIP, install through a Composer
  artifact repository, then verify exact installed identity and vendor autoload.
- [ ] Capture the existing four CI install legs: PHP 8.3/8.4 × Laravel 12/13. Capture
  the ActionBus smoke only for PHP 8.4 + Laravel 13; do not report four smoke legs.
  Preserve the fixture-only policy-stage limitation.
- [ ] Follow the [browser consumer guide](consumers/browser-runtime.md) with the
  recorded input. Build and validate the exact tarball; verify isolated installed
  identity, root ESM import, shipped declarations/typecheck, Vite bundle,
  DriverRegistry smoke and representative deep-import rejection.
- [ ] Record browser tooling tests/typecheck/build and applicable PHP/contract
  checks from the existing [Validate workflow](../.github/workflows/validate.yml).
  Match the CI result to the exact reviewed SHA; distinguish passed, failed,
  skipped, blocked and unverified checks. Node smoke is not real-browser proof.
- [ ] Run the canonical validator `python scripts/validate.py` and publication
  guard `python scripts/check_release_guardrails.py`. Reuse the existing artifact
  suites `python -m unittest scripts.tests.test_laravel_release_candidate` and
  `python -m unittest scripts.tests.test_browser_release_candidate` in suitable
  environments. Do not substitute source-tree execution for installed consumers.

## Evidence and review handoff

- [ ] Retain each archive with its `content-manifest.json` and
  `artifact-evidence.json`, generated by the existing builders. Verify package
  names (`surfacerelay/laravel`, `@surfacerelay/browser-runtime`), candidate version
  and source SHA agree with the recorded inputs for both packages.
- [ ] Independently recompute each archive SHA-256 and content-manifest SHA-256,
  and compare them with `archiveSha256` and `contentManifestSha256` in artifact
  evidence. Review the manifest's file paths, sizes and hashes against the staged
  contents and validated archive. Retain archive filename/size and tool logs.
  Do not claim byte-identical archives across operating systems.
- [ ] Keep evidence outside published package contents. Remove credentials and
  sensitive inputs/outputs from shared logs; do not include registry secrets in
  consumer configuration or review artifacts.
- [ ] Review the complete diff for trust-boundary drift, unsupported compatibility
  claims and unintended package/contract changes. Complete external review and
  finding disposition; record unresolved risks rather than treating green CI as
  release approval.
- [ ] Update STATUS, TASKS and REVIEW_REQUEST with exact revisions, verification
  results, environment limits, archive evidence locations and the next gate.
  The [changelog](../CHANGELOG.md) remains Unreleased until separately authorized
  release work. The [version policy](VERSIONING-COMPATIBILITY.md) separates current
  contracts from proposed future commitments.

## Separate publication go/no-go gate

Local candidate verification does not satisfy this gate. Publication remains
**NO-GO** while the private-reporting gap in [SECURITY](../SECURITY.md) is unresolved.

- [ ] Establish and verify a private vulnerability intake channel and document its
  ownership/process through separately authorized work. Recheck current settings;
  a dated observation is not proof that a channel is available now.
- [ ] Verify intended registry namespace ownership, separately scoped credentials,
  publication authority and an approved first public version. None is established
  by this checklist; do not add credentials or publish while running local proofs.
- [ ] Complete T-804's remaining documentation/review and T-805's integrated
  same-revision/two-artifact verification. Confirm required policy/decision work
  and migration notes are approved; proposed decisions are not silently promoted.
- [ ] Resolve the open plan/implementation PR dependency and obtain explicit merge
  approval before integration; verify the resulting target revision and checks.
- [ ] Obtain separate explicit authorization for any publication, tag or GitHub
  Release, with final exact artifacts, hashes, risks and review evidence attached.

These unchecked items are review requirements, not claims of completed work. No
new release runner, registry integration, support guarantee or runtime contract is
introduced by this document.
